NDAOHODY — API DU BACK, PAR ÉTAPE (ROADMAP-BACK.md, étapes 0 à 8)
Adresse de base : http://localhost:3000
Swagger : http://localhost:3000/api/docs

LES JETONS (TOKENS)
-------------------
/api/v1/auth/otp/verify renvoie 2 jetons :

  accessToken   valable 15 min   -> à mettre dans le HEADER de chaque appel protégé :
                                    Authorization: Bearer <accessToken>
                                    (Swagger : bouton "Authorize" en haut, coller l'accessToken seul)
  refreshToken  valable 30 jours -> ne va JAMAIS dans le header ; seulement dans le BODY
                                    de /auth/refresh et /auth/logout

Quand l'accessToken a expiré (réponse 401), appeler /auth/refresh avec le refreshToken :
on reçoit un nouvel accessToken ET un nouveau refreshToken, qui remplacent les anciens.

[TOKEN APP]   = header  Authorization: Bearer <accessToken reçu par /api/v1/auth/otp/verify>
[TOKEN ADMIN] = header  Authorization: Bearer <accessToken reçu par /api/admin/auth/login>
                (le back-office n'a qu'un accessToken, valable 8 h, pas de refreshToken)
[FORM-DATA]   = body en form-data (envoi de fichier), pas en JSON
{...}         = dans une URL : à remplacer par la vraie valeur (ex. {id du véhicule} -> 8)

Code SMS : il s'affiche dans le terminal du back (SMS_PROVIDER=log).
Données de démo : npm run db:seed (remet la base à zéro).

==============================================================
 ÉTAPE 1 — CONNEXION PAR SMS
==============================================================

POST http://localhost:3000/api/v1/auth/otp
-> Envoie un code à 6 chiffres par SMS au numéro (visible dans le terminal du back).
   1 code par minute, 5 codes par jour, valable 5 minutes.
{
  "telephone": "034 12 345 67"
}

POST http://localhost:3000/api/v1/auth/otp/verify
-> Vérifie le code (3 essais). Crée le compte si le numéro est nouveau ("nouveau": true).
   Renvoie accessToken (15 min) et refreshToken (30 jours) : garde-les pour la suite.
{
  "telephone": "034 12 345 67",
  "code": "code reçu par SMS"
}

POST http://localhost:3000/api/v1/auth/refresh
-> Quand l'accessToken a expiré (après 15 min, les appels renvoient 401) : donne un nouvel
   accessToken et un nouveau refreshToken, sans redemander de code SMS.
   Remplace les deux anciens jetons. L'ancien refreshToken ne marche plus ; s'il est
   réutilisé (vol probable), toutes les sessions de l'utilisateur sont fermées.
   Pas de header Authorization : le refreshToken va dans le body.
{
  "refreshToken": "refreshToken reçu par /otp/verify (ou par le dernier /refresh)"
}

POST http://localhost:3000/api/v1/auth/logout
-> Déconnecte ce téléphone : son refreshToken ne marche plus.
   Pas de header Authorization : le refreshToken va dans le body.
{
  "refreshToken": "refreshToken actuel du téléphone"
}


==============================================================
 ÉTAPE 2 — PROFIL ET MODE                         [TOKEN APP]
==============================================================

GET http://localhost:3000/api/v1/me
-> Renvoie le compte connecté, avec "profilIncomplet" (true s'il manque nom, prénom ou sexe).
(pas de body)

PATCH http://localhost:3000/api/v1/me
-> Complète ou modifie le profil. Pour un nouveau compte, les 3 champs sont obligatoires.
   Le sexe ne peut plus changer une fois choisi.
{
  "nom": "ton nom",
  "prenom": "ton prénom",
  "sexe": "homme ou femme"
}

PATCH http://localhost:3000/api/v1/me/mode
-> Bascule entre l'espace passager et l'espace chauffeur.
{
  "mode": "passager ou chauffeur"
}

PUT http://localhost:3000/api/v1/me/photo                  [FORM-DATA]
-> Envoie la photo de profil (recadrée en 512 x 512). Remplace l'ancienne.
  photo = (fichier image : jpg, png ou webp, 5 Mo max)

POST http://localhost:3000/api/v1/me/devices
-> Enregistre le téléphone pour recevoir les notifications push (MongoDB, collection "appareils").
   Le jeton FCM est l'adresse unique du téléphone chez Firebase (le service de Google qui
   envoie les notifications push). C'est l'app mobile qui l'obtient auprès de Firebase.
   Pour tester maintenant : n'importe quel texte, ex. "fcm-test-123"
   (aucune notification n'est encore envoyée : ça arrive à l'étape 12).
{
  "jeton": "jeton FCM donné par Firebase sur le téléphone",
  "plateforme": "android ou ios"
}

DELETE http://localhost:3000/api/v1/me/devices
-> Le téléphone ne reçoit plus les notifications push (à appeler à la déconnexion).
{
  "jeton": "le même jeton FCM qu'à l'enregistrement"
}

DELETE http://localhost:3000/api/v1/me
-> Supprime le compte (refusé pendant une course). Le numéro est libéré, toutes les sessions sont fermées.
(pas de body)

 ÉTAPE 3 — BACK-OFFICE : COMPTES ET RÔLES
==============================================================

POST http://localhost:3000/api/admin/auth/login
-> Connexion au back-office. Renvoie un accessToken valable 8 h et "permissions"
   (la liste des actions permises à ce compte : le back-office affiche ses menus avec).
   Compte bloqué 15 min après 5 mauvais mots de passe.
{
  "email": "superadmin@ndaohody.test",
  "motDePasse": "Ndaohody2026!"
}
(comptes de démo : superadmin@ndaohody.test, admin@ndaohody.test, invest@ndaohody.test
 — même mot de passe Ndaohody2026!)

GET http://localhost:3000/api/admin/auth/me                [TOKEN ADMIN]
-> Renvoie le compte du back-office connecté (nom, e-mail, rôle) et ses "permissions".
(pas de body)

--- super_admin seulement ---

GET http://localhost:3000/api/admin/accounts               [TOKEN ADMIN]
-> Liste tous les comptes du back-office (et leurs id).
(pas de body)

POST http://localhost:3000/api/admin/accounts              [TOKEN ADMIN]
-> Crée un compte admin ou investisseur. La réponse contient un mot de passe
   temporaire, affiché une seule fois : à donner à la personne.
{
  "nomComplet": "nom complet de la personne",
  "email": "son e-mail",
  "role": "admin ou investisseur"
}

PATCH http://localhost:3000/api/admin/accounts/{id du compte}/active    [TOKEN ADMIN]
-> Désactive (false) ou réactive (true) un compte. Un compte désactivé perd l'accès tout de suite.
{
  "actif": false
}

POST http://localhost:3000/api/admin/accounts/{id du compte}/reset-password   [TOKEN ADMIN]
-> Donne un nouveau mot de passe temporaire et débloque le compte.
(pas de body)


==============================================================
 ÉTAPE 4 — DEVENIR CHAUFFEUR
==============================================================

--- Côté app (le chauffeur)                       [TOKEN APP] ---

GET http://localhost:3000/api/v1/me/documents
-> Montre où en est le dossier chauffeur : statut, numéro de permis, documents envoyés
   (avec un lien vers chaque photo, valable 10 min).
(pas de body)

POST http://localhost:3000/api/v1/me/documents             [FORM-DATA]
-> Envoie le recto du permis avec son numéro. TOUJOURS EN PREMIER.
   Si ce permis appartient à un ancien compte supprimé, cet ancien compte est réactivé
   (la réponse contient "compteReactive").
  type         = permis_recto
  numeroPermis = numéro écrit sur le permis
  fichier      = (photo du recto)

POST http://localhost:3000/api/v1/me/documents             [FORM-DATA]
-> Envoie le verso du permis.
  type    = permis_verso
  fichier = (photo du verso)

POST http://localhost:3000/api/v1/me/documents             [FORM-DATA]
-> Envoie le selfie. Avec les 3 documents, le dossier part en validation (statut "en_attente").
  type    = selfie
  fichier = (selfie du chauffeur)

GET http://localhost:3000/api/v1/me/vehicles
-> Liste les véhicules du chauffeur (et leurs id), le véhicule par défaut en premier.
(pas de body)

POST http://localhost:3000/api/v1/me/vehicles              [FORM-DATA]
-> Ajoute un véhicule, en attente de validation par un admin.
   Un chauffeur peut en ajouter PLUSIEURS (ex. 2 voitures et 1 moto) : refaire cette requête pour
   chaque véhicule, à l'inscription ou plus tard depuis le profil. Le premier devient le véhicule par défaut.
   Si la plaque appartient à un ancien compte supprimé, cet ancien compte est réactivé.
  type            = voiture ou moto
  marque          = marque du véhicule      (facultatif)
  modele          = modèle du véhicule      (facultatif)
  couleur         = couleur du véhicule
  immatriculation = plaque, ex. 4321 TBX
  places          = nombre de places passagers (moto : 1, voiture : 1 à 8)
  photo           = (photo du véhicule, plaque visible)

PATCH http://localhost:3000/api/v1/me/vehicles/{id du véhicule}
-> Modifie la description ou choisit le véhicule par défaut.
   Un véhicule validé dont la description change repasse en validation.
{
  "couleur": "nouvelle couleur",
  "parDefaut": true
}

DELETE http://localhost:3000/api/v1/me/vehicles/{id du véhicule}
-> Retire le véhicule (archivé : sa plaque reste liée au compte).
   Refusé si un trajet publié ou en cours l'utilise.
(pas de body)

--- Côté back-office (validation)                 [TOKEN ADMIN] ---
(super_admin et admin seulement ; un investisseur reçoit 403)

GET http://localhost:3000/api/admin/drivers/applications
-> Liste les dossiers chauffeurs en attente, avec les photos et le numéro de permis.
   Compare le numéro saisi avec la photo du permis avant de valider.
(pas de body)

POST http://localhost:3000/api/admin/drivers/{id de l'utilisateur}/approve
-> Valide le dossier : l'utilisateur devient chauffeur validé et reçoit une notification.
(pas de body)

POST http://localhost:3000/api/admin/drivers/{id de l'utilisateur}/reject
-> Refuse le dossier avec un motif montré au chauffeur, qui renvoie les documents concernés.
{
  "motif": "raison du refus",
  "documents": ["permis_recto"]
}
(documents facultatif : permis_recto, permis_verso, selfie ; sans lui, tout est refusé)

GET http://localhost:3000/api/admin/vehicles/pending
-> Liste les véhicules en attente de validation.
(pas de body)

POST http://localhost:3000/api/admin/vehicles/{id du véhicule}/approve
-> Valide le véhicule et prévient le chauffeur.
(pas de body)

POST http://localhost:3000/api/admin/vehicles/{id du véhicule}/reject
-> Refuse le véhicule avec un motif montré au chauffeur.
{
  "motif": "raison du refus"
}

--- Test anti-fraude (ancien compte retrouvé) ---

1. Connexion avec 034 00 000 03, puis DELETE /api/v1/me
2. Connexion avec un numéro jamais utilisé, ex. 032 99 999 99 (nouveau compte)
3. POST /api/v1/me/vehicles avec immatriculation = 1357 TBD (plaque de l'ancien compte)
-> la réponse contient "compteReactive" : l'ancien compte n°3 revient,
   avec de nouveaux jetons à utiliser à la place des anciens.


==============================================================
 ÉTAPE 5 — CARTES (MAPBOX)                        [TOKEN APP]
==============================================================

Le back appelle Mapbox avec sa propre clé (MAPBOX_ACCESS_TOKEN dans apps/back/.env) :
l'app n'appelle plus Mapbox pour les itinéraires ni la recherche de lieux.
Les routes /geo sont des GET : copier l'URL complète dans Postman, Body = none.

GET http://localhost:3000/api/v1/geo/route?departLatitude=-18.9850&departLongitude=47.5330&arriveeLatitude=-18.9067&arriveeLongitude=47.5253
-> Itinéraire par la route d'Andoharanofotsy à Analakely, avant de publier un trajet.
   Renvoie le chemin, puis tout en bas : distanceMetres (environ 9000), dureeSecondes,
   departSurRoute et arriveeSurRoute (les 2 points ramenés sur la rue la plus proche).
(pas de body)

GET http://localhost:3000/api/v1/geo/places?q=Analakely&session=test-recherche-001&latitude=-18.9067&longitude=47.5253
-> Propose des lieux pendant que l'utilisateur tape (6 au plus, les plus proches d'abord).
   q = ce que l'utilisateur a tapé (2 lettres au moins, sinon liste vide).
   session = un identifiant créé au début de la recherche, le même jusqu'au lieu choisi
   (Mapbox facture par recherche, pas par lettre tapée). latitude / longitude : facultatifs.
   Renvoie [ { "id": "...", "nom": "...", "detail": "..." } ]. Copier un "id" pour la suite.
(pas de body)

GET http://localhost:3000/api/v1/geo/places/{id copié dans la réponse précédente}?session=test-recherche-001
-> Coordonnées du lieu choisi : { "libelle": "...", "latitude": ..., "longitude": ... }.
   Garder la même session que dans la requête précédente.
(pas de body)

GET http://localhost:3000/api/v1/geo/area?latitude=-18.9120&longitude=47.5140
-> Nom du quartier à un point touché sur la carte (jamais un bâtiment) : { "libelle": "..." },
   ou { "libelle": null } si Mapbox ne connaît rien à cet endroit.
(pas de body)

--- Cas d'erreur à vérifier ---

GET http://localhost:3000/api/v1/geo/route?departLatitude=-18.9850&departLongitude=47.5330&arriveeLatitude=48.8566&arriveeLongitude=2.3522
-> Arrivée à Paris : 400 "Ce point est en dehors de Madagascar."
(pas de body)

GET http://localhost:3000/api/v1/geo/route?departLatitude=-18.9067&departLongitude=47.5253&arriveeLatitude=-18.9067&arriveeLongitude=47.5253
-> Départ = arrivée : 400 "Le départ et l'arrivée sont trop proches."
(pas de body)

GET http://localhost:3000/api/v1/geo/places?q=A&session=test-recherche-001
-> Une seule lettre : 200 [] (liste vide, Mapbox n'est pas appelé).
(pas de body)

GET http://localhost:3000/api/v1/geo/route?departLatitude=-18.9850&departLongitude=47.5330&arriveeLatitude=-18.9067&arriveeLongitude=47.5253
-> Sans TOKEN APP (Authorization = No Auth) : 401 "Ta session a expiré. Reconnecte-toi."
(pas de body)

Si une route /geo répond 503 "La carte est momentanément indisponible" : vérifier Internet,
puis lire la ligne [Mapbox] dans le terminal du back (HTTP 401 = MAPBOX_ACCESS_TOKEN invalide,
no answer = pas d'Internet, HTTP 429 = quota Mapbox dépassé).


==============================================================
 ÉTAPE 6 — PUBLIER UN TRAJET                      [TOKEN APP du chauffeur]
==============================================================

Chauffeur de démo : se connecter avec 034 00 000 03 (Rabe Andry, chauffeur validé, voiture 3 places, aucun trajet en route).
Remarque : au démarrage, le back annule les trajets de démo prévus dans le passé (ils ne sont jamais partis).

POST http://localhost:3000/api/v1/trips
-> Publie un trajet qui part MAINTENANT. Le back calcule le chemin avec Mapbox (l'app ne l'envoie pas).
   Le trajet est tout de suite "en_route". Garder son "id" pour la suite.
{
  "type": "immediat",
  "depart": { "libelle": "Andoharanofotsy, rond-point", "latitude": -18.9850, "longitude": 47.5330 },
  "arrivee": { "libelle": "Analakely", "latitude": -18.9067, "longitude": 47.5253 },
  "placesTotal": 3
}

POST http://localhost:3000/api/v1/trips
-> Publie un trajet PRÉVU à l'avance (entre 15 minutes et 15 jours). Statut "publie".
   Un chauffeur n'a qu'un trajet en route à la fois : pour tester celui-ci, annuler d'abord le précédent.
{
  "type": "a_l_avance",
  "depart": { "libelle": "Ivato, aéroport", "latitude": -18.7969, "longitude": 47.4788 },
  "arrivee": { "libelle": "Analakely", "latitude": -18.9067, "longitude": 47.5253 },
  "placesTotal": 3,
  "dateDepart": "date et heure de départ, ex. 2026-11-28T07:30:00+03:00",
  "reserveFemmes": false
}
(reserveFemmes = true seulement pour une conductrice.
 Véhicule : avec UN seul véhicule validé, il est pris tout seul. Avec PLUSIEURS, ajouter
 "vehiculeId": id du véhicule choisi — sans lui, réponse 400 avec la liste dans details.vehicules.)

GET http://localhost:3000/api/v1/me/trips
-> Les trajets du chauffeur connecté, le plus récent d'abord.
(pas de body)

GET http://localhost:3000/api/v1/me/trips/active
-> Le trajet en route du chauffeur, ou null.
(pas de body)

GET http://localhost:3000/api/v1/trips/{id du trajet}
-> Le détail d'un trajet, avec son chemin.
(pas de body)

PATCH http://localhost:3000/api/v1/trips/{id d'un trajet prévu}
-> Change l'heure ou le nombre de places AVANT le départ. Les passagers sont prévenus.
{
  "dateDepart": "nouvelle date et heure, ex. 2026-11-28T08:00:00+03:00",
  "placesTotal": 2
}

POST http://localhost:3000/api/v1/trips/{id d'un trajet prévu}/start
-> « Je pars » : le trajet prévu passe "en_route" (possible dès 30 min avant l'heure prévue).
(pas de body)

POST http://localhost:3000/api/v1/trips/{id du trajet}/cancel
-> Annule le trajet. Les demandes et places réservées sont annulées, les passagers prévenus.
   Refusé si un passager est déjà à bord.
(pas de body)


==============================================================
 ÉTAPE 7 — RECHERCHER UN TRAJET                   [TOKEN APP du passager]
==============================================================

Passager de démo : se connecter avec 034 00 000 11 (Ranaivo Zo, profil complet, aucune réservation).

POST http://localhost:3000/api/v1/trips/search
-> Cherche les chauffeurs qui PASSENT SUR LE CHEMIN du passager (départ et destination sur leur route,
   dans le bon sens). Ici Tanjombato -> Analakely : trouve le trajet n°1 de la démo (Rakoto, en route),
   pas le trajet n°5 (sens inverse). Chaque résultat donne le prix d'une place et le prix total.
{
  "depart": { "libelle": "Tanjombato", "latitude": -18.9600, "longitude": 47.5280 },
  "destination": { "libelle": "Analakely", "latitude": -18.9067, "longitude": 47.5253 },
  "places": 1,
  "quand": "maintenant"
}
("quand" : "maintenant", ou une date ISO pour plus tard ;
 "femmesSeulement": true possible pour une passagère : seulement les trajets réservés aux femmes)


==============================================================
 ÉTAPE 8 — RÉSERVER                               [TOKEN APP]
==============================================================

POST http://localhost:3000/api/v1/reservations                         [passager]
-> Demande des places au chauffeur. Le prix est calculé par le back et figé.
   Le chauffeur a 3 minutes pour répondre, sinon la demande expire.
   Mettre les points "priseEnCharge" et "depose" d'un résultat de /trips/search.
{
  "trajetId": 1,
  "places": 1,
  "priseEnCharge": { "libelle": "Tanjombato", "latitude": -18.9600, "longitude": 47.5280 },
  "depose": { "libelle": "Analakely", "latitude": -18.9067, "longitude": 47.5253 }
}

GET http://localhost:3000/api/v1/me/reservations                       [passager]
-> Les réservations du passager, la plus récente d'abord.
(pas de body)

GET http://localhost:3000/api/v1/me/requests                           [chauffeur]
-> Les demandes qui attendent la réponse du chauffeur (pas encore expirées).
   Pour le trajet n°1 de la démo : se connecter avec 034 00 000 01 (Rakoto).
(pas de body)

POST http://localhost:3000/api/v1/reservations/{id de la demande}/accept   [chauffeur]
-> Accepte : les places sont retirées du trajet, la discussion s'ouvre, le passager est prévenu.
   Deux acceptations sur la dernière place : une seule réussit.
(pas de body)

POST http://localhost:3000/api/v1/reservations/{id de la demande}/refuse   [chauffeur]
-> Refuse avec un motif montré au passager.
{
  "motif": "raison du refus, ex. Je ne passe plus par là"
}

GET http://localhost:3000/api/v1/reservations/{id de la demande}/refusal-reason
-> Le motif du refus donné par le chauffeur.
(pas de body)

GET http://localhost:3000/api/v1/reservations/{id de la demande}
-> Le détail d'une réservation (seulement pour le passager et le chauffeur du trajet).
(pas de body)

POST http://localhost:3000/api/v1/reservations/{id d'une demande expirée}/retry   [passager]
-> Renvoie la même demande au même chauffeur après une expiration (2 fois au plus).
(pas de body)

POST http://localhost:3000/api/v1/reservations/{id de la réservation}/cancel   [passager ou chauffeur]
-> Passager : annule seulement AVANT la réponse du chauffeur (après acceptation : 409).
   Chauffeur : peut annuler un passager jusqu'à sa montée ; les places reviennent au trajet.
   L'autre est prévenu.
(pas de body)
